下面按**“数据 → 存储 → 读取与预处理 → GPU 训练 → 多卡/网络 → 计费与监控”** 的工作流，把前面聊到的硬件和概念整理成一份笔记。重点放在**数据与算力**，并尽量用非计算机科班的语言解释。

# 一、先建立总图：一次训练到底经过什么

一次分钟频 A 股端到端模型训练，大致经过：

**原始数据整理 → 存到云存储 → GPU 服务器读取 → CPU 预处理/组 batch → GPU 前向+反向传播 → 保存模型 → 监控显存、利用率、耗时和费用**

对应硬件/资源：

| 环节 | 主要资源 | 关键问题 |
|---|---|---|
| 数据存放 | OSS/云盘/本地盘 | 存哪里便宜、读取快不快 |
| 数据读取 | 网络、磁盘 IO | 会不会喂不饱 GPU |
| 数据预处理 | CPU、内存 | 32 核够不够、DataLoader 是否高效 |
| 模型训练 | GPU 算力、显存 | 能不能装下、算得快不快 |
| 多卡/多机 | PCIe/NVLink/网络 | 多卡加速是否明显 |
| 计费 | 核时/卡时/包月 | 成本大头在哪里 |
| 监控调优 | nvidia-smi、PyTorch API | GPU 是否被充分利用 |

# 二、计费单位：核时、卡时

### 1. 核时
**1 核时 = 1 个 CPU 核心运行 1 小时。**

它不是硬件性能指标，而是**资源消耗/计费单位**。例如任务用了 32 个 CPU 核心跑 10 小时，就是 **320 核时**。

### 2. 卡时
**1 卡时 = 1 张 GPU 运行 1 小时。**

在 GPU 训练里，GPU 费用通常是大头，所以常按“卡时”理解成本。阿里云上 4090 实例按量付费参考价大致在**几元到十几元/小时**，具体看实例家族、地域和活动；你之前看到的 `ecs.gn8i`（4090、32 核）可先用 **6–8 元/小时**做估算基准。

### 3. 结论
- **核时**主要衡量 CPU 资源。
- **卡时**主要衡量 GPU 资源。
- 对量化训练，**GPU 卡时通常是最贵的部分**，存储费往往只占很小比例。

# 三、CPU、内存：别只盯着 GPU

### 1. CPU 核心、线程、vCPU
- **物理核心**：CPU 里真正独立的计算单元。
- **线程**：一个核心通过超线程技术可同时处理多个指令流。
- **vCPU**：云服务器/虚拟机分配给你的虚拟核心，不等于物理核心，性能可能有差异。

**32 核**对量化金融很实用：特征工程、DataLoader、GBDT、回测、数据清洗都能吃多核。

### 2. 主频、睿频
- **主频**：基础运行频率。
- **睿频**：高负载时自动提升到的更高频率。
- 对大规模并行训练，核心数和内存带宽通常比单核高频更重要；但数据预处理、部分回测也吃单核速度。

### 3. 内存容量与内存带宽
- **内存容量**：能同时装下多少数据表、因子矩阵、缓存。
- **内存带宽**：CPU 从内存取数据的速度。
- 如果 32 核经常跑满、内存吃紧，瓶颈可能不在 GPU，而在 CPU/内存。

### 4. NUMA
多路服务器里，CPU 访问“自己直连”的内存快，访问另一颗 CPU 的内存慢。**跨 NUMA 访问**会拖慢性能。普通单机训练一般不用太操心，但大服务器上要注意。

# 四、GPU：算力的核心，但不是只看 TFLOPS

### 1. GPU 和 CPU 的区别
- **CPU**：核心少但强，擅长复杂逻辑、串行任务、调度。
- **GPU**：核心多但相对简单，擅长大量并行计算，比如矩阵运算、深度学习。

### 2. CUDA Core 与 Tensor Core
- **CUDA Core**：通用并行计算单元。
- **Tensor Core**：专门加速矩阵运算，对深度学习非常重要。

### 3. 算力单位：TFLOPS
**TFLOPS = 每秒万亿次浮点运算**。但要注意：
- 必须看**精度格式**：FP32、FP16、BF16、TF32 等。
- 峰值 TFLOPS 不等于实际速度，实际要看 **MFU（模型算力利用率）**。

### 4. 精度格式
- **FP32**：单精度，精度高、显存占用大。
- **FP16/BF16**：半精度/混合精度常用格式，省显存、提速。
- **TF32**：NVIDIA 在部分矩阵运算中使用的中间精度。
- 训练常用**自动混合精度 AMP**：大部分计算用 FP16/BF16，关键部分保留 FP32。

### 5. 显存：GPU 的“内存”
- **显存容量**：决定模型、优化器状态、batch 数据能不能装下。不够就 **OOM（显存不足）**。
- **显存带宽**：数据从显存搬到计算单元的速度。带宽低，算力再高也可能“等数据”。
- **显存类型**：消费卡常用 GDDR6X/GDDR7；数据中心卡常用 **HBM**，带宽更高。

**RTX 4090：24GB 显存**，适合中小模型训练/微调、原型实验。  
**L20：48GB 显存**，显存更大但 FP16 算力低于 4090，适合“装得下比算得快更重要”的场景。

### 6. 功耗与散热
4090 功耗高，云上实例通常有散热保障；本地机器要注意电源和机箱散热。功耗限制可用 `nvidia-smi -pl` 调整，但会牺牲部分性能。

### 7. GPU 利用率
用 `nvidia-smi` 看。长期低于 60%–70%，说明 GPU 可能在等 CPU 数据、等磁盘 IO 或通信，不一定是 GPU 不够。

# 五、存储：OSS、云盘、数据库怎么选

### 1. 对象存储 OSS
OSS 是阿里云的对象存储服务，类似“云上网盘/数据仓库”。

核心概念：
- **Bucket**：顶层容器，比如 `quant-a-share-data`。
- **Object**：一个文件对象，比如一个 `.parquet` 文件。
- **Region/Endpoint**：地域和访问地址。**GPU 实例和 Bucket 同地域**，走内网，速度快且通常免内网流量费。

特点：
- 容量几乎无限。
- 成本低，标准存储参考约 **0.12 元/GB/月**。
- 适合“一次写入、多次批量读取”的训练数据。

### 2. Parquet
**列式存储格式**。按列压缩和读取，适合大规模表格/时序特征数据，比 CSV 更省空间、读取更快。

### 3. 云盘、本地 NVMe、并行文件系统
- **云盘/EBS**：像云上的硬盘，适合实例系统盘、临时数据。
- **本地 NVMe SSD**：实例本地高速盘，读写快，适合训练时把数据先拷过来。
- **并行文件系统 CPFS/Lustre**：多节点同时高速读写，HPC 常用。你当前单机训练不一定需要。

### 4. 数据库要不要租？
训练阶段**通常不必**先租昂贵数据库。分钟频历史数据主要是“批量顺序读”，用 **OSS + Parquet** 更经济。  
只有在需要**低延迟随机查询、实时推理、频繁切片点查**时，才考虑 Lindorm、ClickHouse 等时序/分析数据库。

### 5. IOPS、吞吐、延迟
- **IOPS**：每秒读写操作次数，小文件/随机读写看它。
- **吞吐**：大文件连续读写速度。
- **延迟**：一次请求响应时间。
训练时如果 GPU 利用率低，可能是存储 IO 或数据加载拖后腿。

# 六、数据加载与预处理：最容易被忽视的瓶颈

### 1. DataLoader
PyTorch 的数据加载器。关键参数：
- **`num_workers`**：并行加载数据的进程数。32 核可先试 **8–16**，再实测调整。
- **`pin_memory=True`**：把数据锁在固定内存，CPU→GPU 传输更快。
- **`persistent_workers=True`**：epoch 间保留 worker，减少重复创建开销。

### 2. 常见现象
`nvidia-smi` 显示 GPU 利用率低，但 CPU 很忙，通常是 **DataLoader/预处理喂不饱 GPU**。这时加 GPU 没用，应先优化数据管道。

### 3. 内存 vs 显存
- **内存**：CPU 用，装原始数据、预处理结果。
- **显存**：GPU 用，装模型、梯度、优化器状态、batch 数据。
两者不要混淆。

# 七、GPU 训练代码：怎么调用、怎么不超限

### 1. 指定 GPU
推荐环境变量：
```bash
CUDA_VISIBLE_DEVICES=0 python train.py
```
代码里：
```python
device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = model.to(device)
data = data.to(device)
```

### 2. 显存优化手段
| 手段 | 作用 | 代价 |
|---|---|---|
| **AMP 自动混合精度** | 省显存、提速，首选 | 少量精度风险 |
| **梯度累积** | 小 batch 模拟大 batch | 训练稍慢 |
| **梯度检查点** | 用重算换显存 | 训练时间增加约 1/3 |
| **及时 `.item()` 释放张量** | 避免累积计算图 | 无 |
| **减小 batch/序列长度** | 最直接防 OOM | 可能影响效果 |

### 3. 监控 API
- `torch.cuda.memory_allocated()`：当前已分配显存。
- `torch.cuda.max_memory_allocated()`：历史峰值。
- `torch.cuda.memory_summary()`：详细显存报告。

目标：**显存峰值 < 90%，GPU 利用率尽量 > 80%**。

# 八、多卡与网络：什么时候才需要考虑

### 1. PCIe
主板/服务器内部连接 GPU、网卡的总线。多卡走 PCIe 通信，带宽有限。

### 2. NVLink / NVSwitch
NVIDIA 的 GPU 间高速直连。**4090 没有 NVLink**，多卡 4090 主要走 PCIe，扩展效率不如专业训练卡。A100/H100 等支持 NVLink，适合大规模多卡训练。

### 3. InfiniBand
HPC/AI 集群高速网络，低延迟、高带宽。单机训练一般用不到；多机训练才关键。

### 4. 多卡扩展效率
1 卡吞吐 vs 4 卡吞吐。如果 4 卡不到 3 倍，要查通信、数据并行策略、batch size。

# 九、阿里云实例怎么选：结合你的场景

| 实例系列 | GPU | 特点 | 对你的意义 |
|---|---|---|---|
| **ecs.gn8i** | RTX 4090，24GB | 国内可用，算力性价比高 | **首选起步**，中小模型训练/原型 |
| **ecs.gn8ia / gn8is** | L20，48GB | 显存大、算力低于 4090；部分仅海外地域 | 仅当 24GB 反复 OOM 且能接受海外时考虑 |
| **ecs.gn8t** | 4090 级别但价格更高 | 定位/配置不同 | 一般不如 gn8i 划算 |
| **A100/H100** | 数据中心卡 | 大显存、NVLink、强互联 | 超大模型/多卡训练才需要 |

**计费建议**：
- 间歇实验：**按量付费 + 用完即停**。
- 长期稳定独占：再看包月/包年。
- 可中断任务：研究抢占式实例，做好 checkpoint。

# 十、训练时间怎么估

粗略公式：$训练时间 \approx \frac{总计算量}{GPU数量 \times 有效算力}$.
Transformer 类：$总FLOPs \approx 6 \times 参数量 \times 训练token数$.
有效算力：$有效算力 = 峰值FLOPS \times MFU$.


MFU 大模型训练做得好约 30%–50%，小模型/数据管道差可能只有 5%–20%。所以**实测 steps/s 比纸面 TFLOPS 更可靠**。

# 十二、最小实践路线

1. **数据**：整理成 Parquet，放 OSS，Bucket 和 GPU 实例同地域。
2. **算力**：国内优先 `ecs.gn8i`（4090，24GB，32 核），按量付费，用完即停。
3. **代码**：`CUDA_VISIBLE_DEVICES` 指定卡；默认开 AMP。
4. **数据管道**：`num_workers` 从 8–16 试，`pin_memory=True`，看 GPU 利用率。
5. **监控**：`nvidia-smi` 看利用率/显存/功耗；PyTorch 看显存峰值。
6. **判断瓶颈**：GPU 利用率低→查 CPU/DataLoader/IO；OOM→AMP/梯度累积/检查点/减 batch；多卡慢→查 PCIe/通信。
7. **成本**：GPU 卡时是大头，存储费占比小；先跑通再优化，不盲目升级硬件。

这份笔记可以当作你之后看云厂商配置单、写训练脚本、判断“算力够不够”的对照表。
